## Key Decisions Made

### 1. Token Expiration: 3600 seconds (1 hour)
**Rationale:**
- Industry standard from Azure Workload Identity documentation
- Matches Azure CSI driver implementation
- Balances security (short-lived) with performance (fewer renewals)

**Source:** Research into secrets-store-csi-driver-provider-azure showed 3600s as the default

### 2. Token Renewal Threshold: 80% of lifetime
**Rationale:**
- Matches Kubernetes kubelet behavior for token renewal
- Prevents token expiration during operations
- 48 minutes for 1-hour tokens gives 12-minute buffer

**Source:** Kubernetes documentation shows kubelet renews at 80% TTL

### 3. Audience: "api://AzureADTokenExchange"
**Rationale:**
- Required by Azure Workload Identity federation
- Standard audience for Azure AD token exchange
- Matches federated credential configuration

**Source:** Azure Workload Identity documentation

### 4. Stubbed Implementation First
**Rationale:**
- Test structure and flow without infrastructure dependencies
- Validate integration points before real API calls
- Faster iteration during development
- Easy to swap stubs for real implementation

**Outcome:** Stubbed version tested successfully, then replaced with real implementation

### 5. Token Logging: Snippet Only (first 5 + last 5 chars)
**Rationale:**
- Security: Don't expose full tokens in logs
- Verification: Enough to see tokens are changing/unique
- Debug: Can identify JWT format (starts with "eyJ")

**Format:** `eyJhb...IzGr0`

### 6. ServiceAccount Impersonation Model
**Rationale:**
- No centralized credentials with access to all vaults
- Reuses existing Azure Workload Identity infrastructure
- Maintains audit attribution in Azure logs
- Reduces blast radius if controller compromised

## Technical Implementation Details

### Token Request Flow

```
Controller (running locally or as pod)
  ↓
Read SecretProviderClass annotations
  ↓
Extract: namespace, serviceAccount, clientID
  ↓
Check TokenCache for valid token
  ↓ (if expired or missing)
Call TokenRequest API for ServiceAccount
  ↓
Kubernetes issues JWT token with:
  - aud: ["api://AzureADTokenExchange"]
  - sub: system:serviceaccount:{namespace}:{serviceAccount}
  - iss: {cluster OIDC issuer}
  - exp: {current time + 3600s}
  ↓
Cache token with expiration
  ↓
Return token (ready for Azure AD exchange in Phase 2.2)
```

### Token Cache Logic

```go
// Check if token needs renewal
isValid := now < (expiration - 20% of lifetime)

// For 3600s tokens:
// - Issued at: 23:37:08
// - Expires at: 00:37:08 (1 hour later)
// - Renew at: 00:25:08 (48 minutes after issue, 12 min before expiry)
```

## Code Patterns and Conventions Established

### 1. Token Cache Pattern
```go
// Thread-safe with RWMutex
type TokenCache struct {
    mu     sync.RWMutex
    tokens map[string]*CachedToken
}

// Check before lock, lock for write
if tc.IsTokenValid(namespace, serviceAccount) {
    tc.mu.RLock()
    token := tc.tokens[key].Token
    tc.mu.RUnlock()
    return token, nil
}
```

### 2. Error Wrapping
```go
if err != nil {
    return "", time.Time{}, fmt.Errorf("failed to request token: %w", err)
}
```

## Questions Asked and Answered

### Q: What is runAsUser: 65534?
**A:** UID for "nobody" user - least privileged non-root user
- Security best practice for containers
- Minimal permissions
- Standard across Linux distributions
- Combined with other security settings (readOnlyRootFilesystem, dropAllCapabilities)

### Q: Can we test locally without deploying to Kubernetes?
**A:** Yes, using local ~/.kube/config credentials
- Controller uses your personal credentials when run locally
- Bypasses ServiceAccount in development
- Allows full functionality testing without deployment
- ServiceAccount only needed for in-cluster deployment

### Q: What is a stub?
**A:** Stand-in for functionality during development
- Has same interfaces as real implementation
- Logs what it would do instead of doing it
- Returns fake but realistic data
- Allows testing structure/flow without dependencies
- Easy to swap with real implementation

### Q: Can we print the token for verification?
**A:** Yes, but only a snippet for security
- First 5 characters + last 5 characters
- Enough to verify format and uniqueness
- Doesn't expose full credential in logs
- Format: `eyJhb...IzGr0`
